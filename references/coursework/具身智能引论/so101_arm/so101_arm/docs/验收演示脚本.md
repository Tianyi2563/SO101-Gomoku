## 1.1 预设姿态与预设动作（键盘控制）

**运行**

```bash
python app_1_1_presets.py --port COM5
```

**步骤**

1. 终端会列出预设姿态和预设动作。先说明：
   > 预设姿态存在 `presets.json` 里，每个姿态就是 6 个电机的目标角度；
   > 预设动作是一串「姿态 + 时长」，比如挥手 = 抬起(1.2s) → 左转(0.7s) → 右转(0.7s) → …
2. 按 `2` → 机械臂从任意初始姿态运动到「抬起」。
3. 按 `1` → 回到「立正（中位）」。
4. 按 `a` → 播放「挥手」动作，动作之间按预设的时长衔接。
5. 按 `[` / `]` → 现场把姿态切换时间从 1.2s 改到 0.8s 或 2.0s，再按 `3` 演示"切换时间可调"。
6. 按 `r` 然后按 `5` → 把机械臂**当前姿态**录进第 5 个槽位（说明预设是"录下来"的，不是写死的）。

**讲解词**

> 姿态之间的运动不是瞬间跳过去的，而是用最小 jerk 曲线（6t⁵-15t⁴+10t³）
> 在设定时间内插值，所以起停都很柔和、舵机不会抖。
> 想限速也可以：程序会按「最大关节行程 ÷ 速度上限」自动算出该用多久。

## 1.2 逆运动学（键盘控制末端走直线）

**运行**

```bash
python app_1_2_ik.py --port COM5
```

**步骤**

1. 按 `p` 打印当前末端位置（相对基座，单位 mm）。
2. 助教指定"向正上方移动 5 cm"→ 按 `r` 五次（每次 10mm），或者先在终端说明步长可调：
   按 `1`/`2`/`3` 切换 5/10/20mm 步长。
3. 每按一次，终端打印新的末端位置；可以让助教拿尺子量。
4. 按 `i` 打印两连杆解析 IK 的原理速览（配合讲解）。
5. 演示**无解反馈**：一直按 `r` 往上走，走到工作空间边界时终端会打印
   `[IK] IK 无解：末端已到达该方向的可达边界`，并且末端停在边界处，而不是乱动或报错崩溃。

**讲解词（重点，助教大概率会问）**

> 键盘只控制**末端位置**，关节角全部由逆运动学算出来。
>
> 先从讲义的两连杆讲起：已知末端 (x, y) 求两个关节角，
> 本质是"以原点为圆心 L1 为半径"和"以 (x,y) 为圆心 L2 为半径"两个圆的交点，
> 所以有**两组解**（肘上/肘下），可达条件是 |L1-L2| ≤ r ≤ L1+L2。
>
> SO101 是 5 个自由度、连杆不在同一平面，几何解太繁琐，实际用的是**数值迭代**：
>
> ```
> e  = p_target - p_current            位置误差
> J  = ∂p/∂q                           位置雅可比（3×5）
> Δq = Jᵀ(JJᵀ + λ²I)⁻¹e               阻尼最小二乘
> q ← clip(q + Δq, 关节限位)           每步都裁进限位
> ```
>
> λ 是**自适应**的：新解让误差变小就调小 λ（趋向牛顿步，收敛快），
> 变大就调大 λ（趋向梯度下降，稳）。固定 λ 会留下 1.3mm 左右的稳态残差，
> 自适应之后能压到 0.1mm 以内。
>
> 5 自由度做 3 维位置任务是冗余的，所以我加了**零空间投影**
> `N = I - J⁺J`，把多余的自由度拉回当前姿态，这样"走直线时腕部不会乱翻"。
>
> 够不着的时候：把步长逐级减半再试，直到找到第一个有解的步长，
> 相当于沿原方向一直走到可达边界——这就是题目要求的"保留尽可能多的原运动方向"。

## 2.1 语音控制 ★本次负责

### 准备

```bash
# 列出麦克风，确认编号（必要时改 config.json 里 voice.input_device）
python app_2_1_voice.py --list-devices

# 先用打字模式确认"指令 -> 动作"这一段没问题
python app_2_1_voice.py --mock --asr text --say "向前移动5厘米" --say "挥手"
```

### 正式演示

```bash
python app_2_1_voice.py --port COM5
```

终端会打印识别后端、可用的预设姿态和预设动作，然后持续监听。

**演示动作（按这个顺序最稳）**

| 步骤 | 你说的话 | 终端会打印 | 机械臂会做什么 |
|------|----------|-----------|----------------|
| 1 | 「挥手」 | `>>> 转录文本：挥手` + `>>> 解析结果：[keyword] 播放预设动作 "wave"` | 播放挥手（抬起→左转→右转→抬起→回中位） |
| 2 | 「向前移动五厘米」 | `[exec] 末端沿 方向 前 (+x) 移动 50 mm` | 末端向前平移 5 cm（IK 算的关节角） |
| 3 | 「向上移动两厘米」 | 同上，方向 `上 (+z)` | 末端抬高 2 cm |
| 4 | 「张开夹爪」 | `[exec] 夹爪 -> 90` | 夹爪张开 |
| 5 | 「向左转」 | `[exec]` 切姿态 | 切到"向左转"预设姿态 |
| 6 | 「停下」 | `[exec] 已停止运动` | 立刻停在当前位置 |

**如果现场嘈杂、识别不稳的备选方案**

```bash
python app_2_1_voice.py --push-to-talk      # 按一下空格录一句，识别完自动停止
python app_2_1_voice.py --seconds 3         # 每句固定录 3 秒
python app_2_1_voice.py --asr text          # 完全不打字直接当识别结果（保底）
```

### 讲解词

> 整条链路是四段：
>
> **① 录音**：`sounddevice` 以 16 kHz 采集，用能量阈值做端点检测——
> 说话前保存 0.24s 的预录缓冲（免得吞字），检测到语音开始录，
> 连续 1 秒静音就认为这句话结束。
>
> **② 识别**：`faster-whisper` 的 small 模型，**本地离线**跑（CPU int8 量化），
> 不依赖网络和 API key，现场也不会因为网络抖动挂掉。识别完把文本打到终端——
> 这就是验收要求的"终端打印语音转录文本"。
>
> **③ 理解**：先用**本地关键字规则**匹配（`parse_command`）：
> 这里有中文数字解析（"两厘米"→2cm）、单位解析（毫米/厘米/米/mm/cm）、
> 方向词最长匹配（"向左转"不会被"左"抢走），还有意图优先级
> （停止 > 夹爪 > 末端移动 > 预设动作 > 预设姿态）。
> 规则的好处是**零延迟、离线、完全可预测**；
> 如果现场说了句规则没覆盖的话，可以打开 LLM 兜底：
> `voice.use_llm_fallback = true` + 设置 `OPENAI_API_KEY`，
> 让大模型返回 JSON 指令。这样既有规则的稳定，又有大模型的泛化。
>
> **④ 执行**：动作类型分三种——
> 切预设姿态/播放预设动作走时间插值；
> 「向前移动5厘米」这种**末端动作**走 IK，把笛卡尔位移翻译成 5 个关节角；
> 夹爪单独控制。

### 助教可能追问

**Q：为什么不用大模型直接端到端控制？**
> 一是延迟：LLM 一次调用几百毫秒到几秒，而关键字规则是微秒级，说完就动；
> 二是可靠性：验收现场网络不一定稳，规则是纯本地的；
> 三是可解释：规则匹配的结果可以明确打印出"匹配到哪个意图、哪个参数"，
> 大模型可能给出一个不存在的姿态名。所以我做成"规则优先、LLM 兜底"。

**Q：识别错了怎么办？**
> 终端会打印转录文本和解析结果，一眼就能看出是哪一步出错：
> 如果转录错了，是 ASR 的问题（换 medium 模型、离麦克风近一点、调 energy_threshold）；
> 如果转录对但解析错了，是规则的问题（补一条同义词即可，`parse_command` 里加别名）。
> 两种错误是分开可见的，排查很快。

**Q：说话到动作有多快？**
> 录音结束后 CPU 上 small 模型识别一句话大约 0.5~1.5 秒，规则解析忽略不计，
> 所以从说完到机械臂开始动大约 1~2 秒。

## 2.2 基于视觉的闭环控制 ★本次负责

### 准备

```bash
# 1. 打开一个全屏黑球当靶子（也可以用它给的图）
python tools/show_ball_screen.py --radius 90

# 2. 确认摄像头
python app_2_2_vision.py --list-cameras

# 3. 只做检测调试：画面里球应被绿圈框住 + 显示 du/dv
python app_2_2_vision.py --probe
```

`--probe` 阶段要确认两件事：

* 球的绿圈稳定跟着球走（不稳就调 `--black-threshold`，屏幕暗就加大，比如 90~110）；
* 画面里没有别的黑色圆形被误检（有就调 `--circularity` 到 0.75）。

### 正式演示

```bash
python app_2_2_vision.py --port COM5 --pre-pose forward
```

`--pre-pose forward` 是让机械臂先摆到"前伸"姿态，正对屏幕。

**演示动作**

1. 启动后，机械臂会一步一停地朝黑球移动，终端每行打印：
   ```
   [03] du=-52.0px dv=-37.0px R= 64.8px (1.00x) -> 末端位移 ( +0.0, +20.4, +14.5) mm
   ```
   分别是：画面里球相对中心的水平/垂直偏差、球的像素半径、以及这一步末端走多少毫米。
2. 收敛后终端打印 `[vision] 已完成对准：|误差| = 12px <= 25px`。
3. **关键演示「闭环」**：用方向键把屏幕上的黑球挪到另一个位置
   （在 `tools/show_ball_screen.py` 窗口里按方向键），重跑一次；
   或者演示过程中直接挪球，机械臂会朝新位置继续移动。
4. 也可以把球挪得远一点（球变小），末端会主动往前靠——说明**距离**也在闭环里。

### 讲解词

> 这条链路的每一步都是"看 → 算 → 动 → 再看"，也就是**闭环**：
>
> **① 看**：OpenCV 抓一帧 → 灰度 → 阈值分割把暗的区域抠出来
> → 形态学开闭运算去掉噪点 → 找轮廓。然后三个条件筛：
> 面积（太小是噪点）、圆度 `4πA/P²`，还有**填充率** `A/(πr²_外接圆)`。
> 最后一个很关键：形态学运算会把方形的角磨圆，光看圆度区分不开黑方块和黑球，
> 而填充率对圆是 1.0、对方块只有 0.64，区分得非常干净（测试里有这条用例）。
>
> **② 算**：把球心和画面中心的像素偏差，映射成末端坐标系里的位移：
>
> ```
> Δp = gain_xy · du · image_right_axis      # 左右
>    + gain_z  · dv · image_down_axis       # 上下
>    + gain_depth · (1 - R/R_ref) · toward_ball_axis   # 远近（球越大说明离得越近）
> ```
>
> ③ **动**：这个 Δp 交给 IK 反解成关节角，末端走一小步（限幅 28mm）。
>
> ④ **再看**：走完重新抓一帧，误差应该变小，再走下一步。
>
> 闭环的好处：手眼映射系数不需要标定得很准，
> 就算某个系数偏大偏小，反馈也会把它纠正过来。
> 我还加了一层保险：如果连续两步误差反而变大，说明那个方向的符号装反了，
> 程序会**自动翻转该方向的映射**并打印提示——所以相机装反了也能自己跑对。
>
> 走不动的时候（到工作空间边界）不会卡死：会尝试换方向重试；
> 演示只要求"运动方向明显朝向黑球"，这个行为已经满足要求。

### 助教可能追问

**Q：为什么不用深度学习做检测？**
> 目标很明确（屏幕上最黑最圆的东西），传统视觉方法几毫秒就能算完、
> 不需要训练数据、行为完全可解释（每个候选的圆度、填充率都能打印出来）。
> 用深度学习反而引入模型部署和数据标注的负担。

**Q：相机和末端之间的坐标关系怎么来的？**
> 相机固定在手爪上，相对末端的安装关系是**固定**的，
> 所以我用三个方向向量描述：图像右对应末端哪个轴、图像下对应哪个轴、
> 球变大对应末端前进还是后退。这三个向量就是 `config.json` 里
> `vision` 段的 `image_right_axis` / `image_down_axis` / `toward_ball_axis`。
> 装配方向变了改这三个向量即可；程序还能自动纠错。

**Q：这种方式能抓东西吗？**
> 现在做的是"对准"（位置闭环）。要真的抓球，还需要在末端闭合时判断半径阈值，
> 以及一个"球心在画面中心 + 球足够大"的停止条件——框架已经具备，
> 加上 `arm.set_gripper()` 就能抓。课程验收只要求"运动方向明显朝向黑球"。

**Q：球被遮挡一帧会怎样？**
> 检测不到球时程序**原地等待、不做任何动作**（打印 `没有检测到黑球`），
> 不会瞎走。这也是闭环的一个好处：拿不到反馈就保持现状。

**加分话术（时间够就说）**

> 四个功能其实是**同一套抽象**：所有动作最后都归结为"6 个电机的目标值 + 用多久到达"。
> 键盘、语音、视觉都只是产生目标的**前端**；IK、插值、限位、伺服循环是共用的**中台**。
> 所以我加一个语音指令或一个视觉目标，不需要动控制层的代码——
> 2.1 的语音动作和 2.2 的视觉移动，调用的都是 1.1 / 1.2 里那套 `ArmController`。
